# 行星发动机 · 工厂自动化系统 设计文档

> 目标:在现有 three_planet(球形行星 + LOD 地形 + 太阳系 N-body + 挖掘机/卡车 agent)之上,做一套 **戴森球计划 / 异星工厂式** 的采集→生产→科技→建造玩法,最终目标是造出 **行星发动机**,燃烧星球物质喷出废料产生推力,把行星推离太阳系(《流浪地球》设定)。
>
> 本文只做 **需求细化 + 框架/架构设计 + 分阶段落地计划**,不写实现代码。核心诉求是 **高扩展性**——所以先把数据驱动 + ECS 的骨架定好,后续加"新矿物 / 新建筑 / 新配方 / 新科技"只改数据、不改引擎。
>
> 相关既有文件:`src/planet.js`(行星 + 四叉树 LOD + `heightAt`/`baseHeightAt` + `applyEdit` edits)、`src/terrain.js`(地形/颜色)、`src/excavators.js`(挖机/卡车 agent 状态机 + InstancedMesh)、`webs/solar_system/nbody.js`(轨道物理)、`webs/*/main.js`(两个 App)。

---

## 0. 一句话愿景

从"星球上只有矿"开始 → 手动/自动采矿 → 建冶炼与制造工厂 → 用物流把中间品串成流水线 → 做研究点亮科技树 → 解锁行星发动机科技 → 分级流水线造发动机零件 → 用特殊运输汇集到组装场 → 组装 → 点火 → 发动机持续燃烧星球物质、向后喷废料 → 反作用力改变行星轨道 → 逃离太阳系。

## 1. 需求细化

### 1.1 资源与物品(Item)
- **原始资源**:埋在地表/地下的矿(铁、铜、硅石、钛、稀土、可燃冰/碳、放射性矿……)。用现有地形做"矿脉"分布(见 §4.1)。
- **中间品**:铁锭、铜锭、钢、玻璃、电路板、电机、结构件、燃料、推进剂……
- **发动机专用件**(高级、多级组装):重元素聚变芯、约束磁环、喷口结构、支撑塔架、控制核心……
- **物品是纯数据**:`{ id, 名称, 堆叠上限, 体积, 图标, 分类, tags }`。所有物品在 `items` 注册表里定义(JSON),不写死在代码里。

### 1.2 采集(Mining)
- 矿机(Miner)放在矿脉上,按 tick 产出对应矿物到自身输出缓冲。
- **两种采集来源**,统一到"产出物品":
  1. 矿脉节点(有限或近似无限储量)。
  2. 直接"啃地形":复用挖掘系统(`applyEdit` 挖低地形)把体积换算成物质产量——这与"发动机烧星球物质"闭环呼应(挖掉的体积 = 拿到的物质)。
- 复用现有 **挖机/卡车 agent**:挖机→矿机的一种表现;卡车→物流的一种表现(见 §1.4)。

### 1.3 生产与配方(Production / Recipe)
- 建筑类型:矿机、冶炼炉、制造台、组装机、化工厂、研究站、发电站、存储仓、物流站、发动机部件……
- **配方(Recipe)= 数据**:`{ id, 输入[{item,数量}], 输出[{item,数量}], 耗时(tick), 需要的建筑类型, 耗电 }`。
- 建筑运行 = 一个通用的"配方执行器":输入齐 + 有电 + 输出没堵 → 每 tick 推进进度 → 完成产出。**所有机器共用同一套执行逻辑**,差异只在配方数据与建筑参数。

### 1.4 物流(Logistics)——"特殊的运送方式"
球面上"传送带"很别扭(测地线路径、拐弯、分合流都难)。建议 **以 agent 运输为主干**,直接复用/推广 `ExcavatorSystem` 的架构:
- **运输 agent(卡车 / 无人机 / 轨道运输舱)**:在"产出建筑"与"消耗建筑"之间沿大圆往返搬运物品(挖机↔卡车已验证这套 状态机 + InstancedMesh + 大圆移动)。
- **存储仓 / 缓冲**:节点上的库存组件。
- 后期可选:**短程传送带**(沿测地线的一小段,做局部紧密流水线);**行星尺度的"环形轨道运输"**(赤道/经线大环)。
- "组装发动机的特殊运输":大件用专用重载运输舱 + 汇集到组装场的多段路径,是运输 agent 的一个特化策略(Strategy)。

### 1.5 电力 / 能量(Power)
- 建筑耗电;发电站(风、地热、聚变……)供电。
- 简化为**电网分组**:一个电网的总发电 ≥ 总需求则满载,否则按比例降速(异星工厂式)。
- 电力是很多工厂游戏的核心约束,建议早期就预留 `Power` 组件与 `PowerSystem`,但可先做"无限电"占位、后填。

### 1.6 科技树(Research / Tech)
- 研究站消耗"科学包"(由流水线生产)→ 积累研究点 → 解锁科技。
- **科技 = 数据**:`{ id, 前置[], 消耗{科学包}, 解锁[建筑/配方/参数升级] }`。
- 解锁通过 **事件总线** 广播 → 相关系统(建造菜单、配方表)据此启用。行星发动机是科技树末端的一个大节点(可能拆成多个前置:重工业、可控聚变、行星级结构、轨道力学……)。

### 1.7 行星发动机(Planet Engine)——终局
- **建造**:分级流水线造出各部件 → 特殊运输汇集到组装场 → 组装成一台发动机(可能需要建很多台,分布在行星某一面以合成同向推力)。
- **点火**:满足前置(部件齐、燃料供应、控制核心在线)后可点火。
- **运行 = 消耗物质 + 产生推力**:
  - 每 tick 消耗"星球物质/燃料"(可与采矿/挖地形挂钩:发动机在吃星球)。
  - 向"行星运动反方向 / 指定方向"喷出废料 → 产生推力 `F`。
  - 推力叠加到行星的 N-body 加速度上(见 §4.2)→ 逐渐改变轨道 → 达到逃逸速度 → 离开太阳系。
- **视觉**:巨大的喷口 + 等离子/废料喷流(粒子或 shader),行星被推动时轨道线可视化变化。

### 1.8 交互 / UI
- **建造模式**:选建筑 → 在地表放置(方向 + 切平面朝向,复用挖掘选区的射线拾取)→ 合法性检查(地形坡度、是否重叠、是否在矿上)。
- 蓝图 / 复制粘贴(后期)。
- 面板:物品/配方/科技/电力/发动机进度;建筑信息弹窗(库存、配方、状态)。
- 存档 / 读档(必需,工厂游戏一玩几小时)。

## 2. 架构总原则(为什么这样设计)

1. **模拟与渲染分离**:模拟核心(纯数据 + 逻辑,零 three.js 依赖)放 `src/factory/`;渲染层订阅模拟状态。这样可测试、可跑在 Worker、可被 planet_system 与 solar_system 两个 App 共用。
2. **ECS(Entity-Component-System)**:工厂游戏实体量大、种类多、行为可组合,ECS 是业界标准。组合优于继承,加新行为 = 加组件 + 系统,不动老代码。
3. **数据驱动**:物品/配方/建筑/科技全部是 JSON 注册表。加内容不改引擎——这是"高扩展性"的核心。
4. **固定步长 tick**:模拟用固定 dt(如 20 Hz)累加器推进,与渲染帧率解耦(渲染做插值)。保证不同帧率下逻辑一致、可确定性存档。
5. **一切可序列化**:组件是纯数据 → 存档 = 序列化组件 + 注册表版本号。

## 3. 框架设计:ECS + 数据驱动

### 3.1 目录结构(建议)
```
src/factory/
  core/
    world.js          # ECS 世界: 实体表 + 组件仓 + 系统调度 + tick 循环
    components.js     # 组件定义(纯数据结构/工厂函数)
    events.js         # 事件总线(Observer)
    registry.js       # 注册表: items/recipes/buildings/tech (数据驱动)
    save.js           # 序列化/反序列化
    spatial.js        # 球面空间索引(邻居/碰撞/拾取)
  systems/
    production.js     # 配方执行(矿机/冶炼/制造/组装通用)
    logistics.js      # 运输 agent 调度(推广自 excavators)
    power.js          # 电网供需
    research.js       # 科技进度 + 解锁广播
    engine.js         # 行星发动机: 消耗物质→推力
    placement.js      # 建造/拆除(Command)
  data/
    items.json  recipes.json  buildings.json  tech.json
  render/
    factory_render.js # 把 world 里的建筑/agent/物品渲染成 InstancedMesh(接 three.js)
```
> `render/` 是唯一依赖 three.js 的地方;`core/`+`systems/`+`data/` 纯逻辑,可单测、可进 Worker。

### 3.2 实体 / 组件(示例)
实体 = 一个整数 id。组件 = 挂在 id 上的纯数据。典型组件:

| 组件 | 字段 | 用途 |
|---|---|---|
| `Anchor` | `dir(单位向量)`, `yaw`, `tilt` | 球面上的位置与朝向(复用 `heightAt` 求落地半径) |
| `BuildingType` | `typeId` | 指向 buildings 注册表(Flyweight 共享类型数据) |
| `Machine` | `recipeId`, `progress`, `active` | 配方执行状态 |
| `Inventory` | `slots[]`, `cap` | 库存(输入/输出缓冲、仓库) |
| `Power` | `demand`, `supply`, `gridId` | 电网 |
| `Agent` | `kind`, `state`, `cargo`, `target`, `path` | 运输/施工个体(状态机,复用挖机/卡车) |
| `OreNode` | `itemId`, `amount` | 矿脉 |
| `Engine` | `thrustDir`, `throttle`, `fuelRate`, `online` | 行星发动机 |
| `Renderable` | `meshKind`, `instanceId` | 供渲染层批量实例化 |

### 3.3 系统(每 tick 按序执行)
`PowerSystem → ProductionSystem → LogisticsSystem → ResearchSystem → EngineSystem → PlacementSystem(事件驱动)`。系统只遍历"拥有所需组件"的实体,互相通过组件数据 + 事件总线解耦。

### 3.4 用到的设计模式
- **ECS / 组合优于继承**:实体行为由组件拼装。
- **Registry + Flyweight**:类型数据(物品/建筑/配方)集中共享,实例只存变化态。
- **Factory(工厂方法)**:按 `typeId` 从注册表建实体(建筑/物品)。
- **Strategy(策略)**:机器行为、运输方式(卡车/无人机/轨道舱)、发动机推进模型可换实现。
- **State(状态机)**:运输 agent、发动机点火流程——直接复用 `excavators.js` 里已验证的状态机写法。
- **Observer / EventBus**:科技解锁、建造完成、发动机点火等跨系统通知,避免硬耦合。
- **Command**:建造/拆除/蓝图 → 可撤销、可批处理、可录制。
- **Object Pool**:物品实例、运输 agent、粒子复用,减少 GC。
- **固定步长 + 累加器**:确定性模拟(存档一致)。

### 3.5 渲染层(接 three.js,复用现有经验)
- 每种建筑一个 **InstancedMesh**(复用 `excavators.js` 的 `_makeInstanced` + 逐帧写实例矩阵/颜色)。
- 建筑落地:`Anchor.dir` → `radius + heightAt(dir)*maxHeight` 求世界位置;切平面基 `makeBasis` 定朝向(与挖机一模一样)。
- 运输 agent、物品在途:小 InstancedMesh + 头顶指示(已有"箭头标记"经验)。
- 太阳系里在浮动原点空间定位(用 `planet.position`,已有先例)。
- 发动机喷流:粒子系统或 shader pass(参考现有 effects.js 的全屏 pass 经验)。

## 4. 与现有系统的具体接入点

### 4.1 采矿 / 矿脉 与地形
- **矿脉分布**:用一层噪声(复用 terrain 的 noise 思路)或手放,得到"某方向是什么矿、储量多少"。可做成 `terrain` 的扩展函数 `oreAt(dir)`。
- **挖地形取物质**:复用 `planet.applyEdit(localPos, radius, depth, falloff, dry)`——挖掉的体积按公式换算成物质产量,和"发动机烧星球"共用一套"星球总质量在减少"的账。
- **放置合法性**:`baseHeightAt`/`heightAt` 判坡度与陆海;拾取射线复用挖掘选区的 `raycaster.intersectObject(planet)`。

### 4.2 行星发动机推力 → 轨道(接 `nbody.js`)
`NBodySystem.step(dt)` 是 velocity-Verlet:先 `computeAccelerations()`(引力),再 drift/kick。**推力接入最干净的方式**:给 `Body` 增加一个"外力累加器",在 kick 前把 `推力加速度 = F/m` 叠加到 `body.acc` 上。
```
// 伪代码(nbody 侧加 externalAcc, EngineSystem 每 tick 写入)
computeAccelerations();           // 引力
for (body of bodies) body.acc.add(body.externalAcc);   // 叠加发动机推力
... kick ...
```
- 推力方向:一般沿"轨道切向反方向"减速→降轨,或按策略指定;喷口朝向决定推力反方向。
- `F = 质量流率 × 排气速度`(火箭方程思路);持续推力逐渐改变行星速度矢量 → 半长轴/离心率变化 → 达到相对恒星的逃逸速度即离开太阳系(可用能量判据 `½v² - GM/r > 0` 判定"已逃逸")。
- 行星总质量随燃烧缓慢下降(可选,增强真实感;注意别让引力解算发散)。
- planet_system(单星)可做"简化轨道/直接演示推力效果";真正的"离开太阳系"在 solar_system 里跑。

### 4.3 复用挖机/卡车 agent
`ExcavatorSystem` 的:大圆移动 `_moveTo`、球面随机点、状态机、InstancedMesh、头顶标记、地形提交节流——都是物流/施工 agent 的现成基础。建议把它**重构进 `src/factory` 的 agent 框架**(挖机/卡车成为 agent 的两种 kind),避免两套并行。

## 5. 分阶段落地计划(每阶段可玩/可验证)

> 原则:每个里程碑都产出"能跑起来看到东西"的最小闭环,框架一次到位、内容逐步加。

- **M0 · 引擎骨架(纯逻辑)**
  ECS world + 固定 tick + 注册表 + 事件总线 + 存档骨架 + 球面放置/空间索引。无内容,单测通过。
- **M1 · 采矿闭环**
  矿脉 `oreAt` + 矿机(放置→产矿到自身库存)+ 建筑 InstancedMesh 渲染 + 建造/拆除(Command)。能在地表放矿机、看到它产矿。
- **M2 · 物流**
  运输 agent(复用挖机/卡车)在矿机↔仓库间搬运;仓库库存 UI。串起"矿机→仓库"。
- **M3 · 生产/流水线**
  冶炼炉 + 制造台 + 配方执行器(通用)。矿→锭→零件的多级流水线跑通。
- **M4 · 电力**
  Power 组件 + 电网供需 + 发电站;缺电降速。(可与 M3 并行/后置)
- **M5 · 科技树**
  研究站 + 科学包配方 + 科技数据 + 解锁事件 → 建造菜单/配方动态启用。
- **M6 · 行星发动机·建造**
  发动机部件(多级组装)+ 专用重载运输 + 组装场 + 组装完成事件。造出一台(未点火)发动机实体。
- **M7 · 点火与推力**
  EngineSystem:消耗燃料/物质 → 写 `externalAcc` → nbody 叠加推力 → 轨道可视化变化;喷流特效。
- **M8 · 逃逸终局**
  多台发动机合成推力、总量/效率平衡、逃逸判据与"离开太阳系"结算;流浪地球式的进度/剧情面板。
- **M9 · 打磨**
  蓝图/复制、存档健壮性、性能(实例化/Worker/LOD 隐藏远处工厂)、平衡性调参、音效/UI。

## 6. 高扩展性检查清单(设计时就满足)
- [ ] 加"新矿物/新物品" = 只改 `items.json`。
- [ ] 加"新配方" = 只改 `recipes.json`。
- [ ] 加"新建筑" = `buildings.json` + (需要新行为时)加一个组件/系统,老建筑不受影响。
- [ ] 加"新科技" = `tech.json` + 声明解锁项。
- [ ] 加"新运输方式" = 加一个 Strategy,不动调度框架。
- [ ] 换"推进模型" = 换 Engine 策略,不动 nbody。
- [ ] 模拟核心零 three.js 依赖 → 可单测 / 可进 Worker。
- [ ] 存档 = 序列化组件 + 版本号,升级有迁移点。

## 7. 主要难点与风险
- **性能**:成百上千建筑/agent/物品 → 必须 InstancedMesh + 固定 tick + 远处工厂 LOD 隐藏 + 可能把模拟放 Worker。ECS 的数据局部性有利。
- **球面物流**:没有平面网格,靠 agent + 测地线;分合流、拥堵、寻路要克制复杂度(先直线大圆,后期再优化)。
- **轨道稳定性**:持续推力 + 可能的质量变化,别让 velocity-Verlet 发散;推力量级要与 G/尺度匹配(参考现有 `worldScale`)。
- **数值/尺度**:太阳系用了浮动原点 + 动态 near/far;工厂在行星表面(近距),渲染要落在这套体系内。
- **存档兼容**:数据驱动 + 版本号 + 迁移,避免一改配方老存档报废。
- **玩法平衡**:配方链、科技节奏、发动机成本——这是长期调参活,数据驱动让调参不用改代码。

---

## 8. 建议的技术选型
- **语言/运行**:延续现有 vanilla ES modules + three.js(0.160,CDN importmap),无需引入构建工具。
- **ECS**:自研轻量 ECS(几百行,贴合需求、易存档)优先;或按需引入 `bitecs` 这类极简库(需评估 importmap 兼容)。
- **数据**:JSON 注册表 + 运行时校验(缺字段给默认)。
- **模拟**:主线程固定 tick 起步;实体量上来后把 `core/systems` 迁进 Web Worker(与地形 worker 同思路)。
- **渲染**:InstancedMesh + 现有 LOD/浮动原点/大气管线复用;发动机喷流用粒子或全屏 pass。
- **存档**:localStorage(小)/ 导出 JSON 文件(大),与现有 presets 导出/导入一致。

## 9. 落地第一步(建议)
先做 **M0 + M1 的最小切片**,把框架钉死:
1. `src/factory/core/`:world(实体/组件/系统/tick)、registry、events。
2. `data/items.json`、`buildings.json`、`recipes.json` 各放两三条样例。
3. `render/factory_render.js`:一种建筑的 InstancedMesh + 放置(复用挖掘拾取)。
4. 在 planet_system 里挂一个"工厂"面板:选建筑 → 点地表放置 → 看到矿机产矿(数字跳动)。
这一步验证"数据驱动 + ECS + 球面放置 + 实例化渲染"整条链,之后每个里程碑都是往这套骨架里加数据/系统。

---

## 10. 需求细化(第二轮:采集 / 物流 / 电力 / 科技 / 发动机)

> 本轮把 §1 的粗需求按实际玩法拍定,并给出对应的数据模型、组件、系统与扩展点。凡是"加内容不改引擎"的地方都标注了数据项。

### 10.1 采集:分层矿脉 + 表土覆盖 + 可扩展机种

**核心:矿在地形下面,得先挖开表层才能拿到。** 把地形从"单值高度场"扩展出一个**柱状分层**观念:

- 每个方向 `dir` 有一根"物质柱",从地表往下依次是:**表土(overburden,废土/低价)→ 岩层 → 矿层(可多层、多种矿)→ 深层高能物质(后期发动机燃料)**。
- 生成逻辑 `oreColumn(dir)`(与地形 noise 同源):返回该方向各层 `{ itemId, 相对地表的深度区间[d0,d1], 密度/储量, 硬度 }`。分布规则数据化(哪种矿在什么纬度/板块/深度更常见)。
- **采集与"挖到多深"耦合**:挖掘机每 tick 在作业点用 `planet.applyEdit(...)` 把地形挖低 Δd,挖穿的这一段落在哪层 → 产出该层物质。于是天然形成"先剥离表土 → 挖到矿层才出矿"的过程;露天矿=削一大片露出矿层,深井=局部挖深。
- **硬度 gate**:高硬度矿层需要更高级钻机才能挖动(低级机在硬层上产出=0 或极慢)→ 科技/机种进阶的抓手。

**机种高扩展(挖掘机 / 运输机都要)**:统一到"数据驱动的 agent 类型注册表"。

| 数据(machineTypes.json) | 字段(示例) |
|---|---|
| 通用 | `id, kind(miner/hauler/builder/…), 外形mesh, tier, 耗电, 造价` |
| 挖掘类 | `挖速, 作业半径, 可挖硬度上限, 单次装载量` |
| 运输类 | `运力, 移动速度, 可走地形, 装/卸速率` |

- 挖机/卡车/无人机/建造机都是 `Agent` + 一个 **行为策略(Strategy)**(`MineBehavior` / `HaulBehavior` / `BuildBehavior`)。加新机种 = 加一条 `machineTypes` 数据(+ 需要新行为时才加一个策略)。
- 直接**重构 `excavators.js`**:现有挖机/卡车成为 agent 框架里的两个 `kind`,`_moveTo`/状态机/InstancedMesh/头顶标记/地形提交节流全部保留复用。

新增组件:`OreColumn`(或做成 terrain 扩展函数)、机种参数走注册表(Flyweight)。

### 10.2 物流:三层运输(带 / agent / 定制路线)

| 层级 | 场景 | 机制 | 复用 |
|---|---|---|---|
| **L1 传送带** | 厂区内部、相邻机器紧密流水线 | 沿测地线的短带,物品匀速前进;端口做插入/取出,分合流用简单端口逻辑 | 新做(短带,复杂度可控) |
| **L2 agent 短途** | 厂区之间、中等距离、不值得铺固定线 | 点对点 hauler 往返(大圆移动) | 直接用挖机/卡车 agent |
| **L3 定制长途路线** | 远距离枢纽间、跨半球 | 玩家设"运输站"(source/sink)+ 定义路线(站点序列)+ 货物清单;专用运输器沿固定路线循环装卸 | 类 DSP 物流塔 / 异星工厂火车 |

- **统一抽象**:所有运输方式都往同一套"库存端口(port)"读写;`LogisticsSystem` 只关心"把有货的 port 送到缺货的 port",**具体方式是可换的 Strategy**(`BeltStrategy` / `AgentStrategy` / `RouteStrategy`)。
- 新增组件:`Belt`(段几何 + 上面的物品队列)、`TransportStation`(角色 source/sink + 货单)、`TransportRoute`(站点序列 + 绑定的运输器)。
- 扩展点:加"新运输器"= 机种数据 + 走 L2/L3 策略;加"新路线"= 运行时数据,不改引擎。

### 10.3 电力:输电塔覆盖 → 自动连线(无手动布线)

**上帝视角只放塔,不拉线。**

- 放 **输电塔(PowerTower)**,每塔一个覆盖角半径 `range`。
- **建筑自动接入**:落在某塔 `range` 内的用电建筑 → 自动生成一条视觉输电线(塔→建筑)并并入该塔的电网。建筑移动/新建/拆除时增量更新覆盖关系。
- **塔与塔自动组网**:两塔角距 < `range`(或覆盖交叠)→ 连成同一电网(**并查集 / 连通分量**)。玩家只管铺塔把区域盖住,电网与连线自动成形。
- **供需**:每个电网 `总发电 vs 总需求` → 满足率 `sat=min(1, 发电/需求)`;不足则该网内建筑 `progress *= sat`(按比例降速,异星工厂式)。
- 数据:塔 `range/容量`、建筑 `demand`。渲染:塔→建筑、塔→塔连线用 `LineSegments`/InstancedMesh 批量画,**只在覆盖关系变化时重建**,不每帧算。
- 新增组件:`PowerTower(range, gridId)`、`Power(demand, supply, gridId)`;系统 `PowerSystem`(重建覆盖/电网连通 + 每 tick 结算满足率)。

### 10.4 科技:小人发展度驱动(不是直接消耗物质)

**科技水平 = 殖民地(小人)的发展程度,而非"花科学包兑换"。** 这把玩法从"堆产线"扩展成"经营殖民地"。

- 新增 **人口 / 小人系统(Colonist)**:小人有数量,有**需求**(住房 / 食物 / 能量 / 消费品 / 就业 / 环境)。需求被满足 → 满意度↑ → 人口增长;不满足 → 停滞/流失。
- **发展度 DevelopmentLevel**(可多维:工业/民生/科研)= 由 `人口规模 × 满意度 × 基础设施与产出多样性` 派生的指标,随殖民地经营自然增长。
- **科技解锁 = 发展度达阈值 + 附加条件**(例:已建成某类建筑、累计产出过某物品)。达标 → 事件总线广播解锁 → 建造菜单/配方动态启用。
- 小人复用 agent 框架(球面上的个体);岗位/通勤/住房分布可后期做。
- 数据:需求项与权重、人口增长曲线、发展度公式、各科技的阈值+附加条件,全在 `tech.json`/`population.json`。
- 系统:`PopulationSystem`(人口/需求/满意度/增长)→ 派生 `DevelopmentLevel` → `ResearchSystem`(据阈值解锁)。
- 与生产的关系:生产线不再"直接喂研究站",而是**供给小人的消费品/民生需求** → 间接推高发展度 → 解锁科技。科研建筑更多是"提升发展度上限/速度"的加成设施。

### 10.5 行星发动机:分级建造(多阶段 + 多台)

一台发动机 = 一个 **分阶段建造工程(ConstructionProject)**,阶段是数据(build-plan),按序推进,每阶段有前置/输入/进度/完成事件:

1. **选址 + 地形平整**:圈一块地,要求平整到规格(用挖掘机/整平 `level` 编辑把该区削平,**或直接用采矿啃出来的空地**)。达标才进下一阶段。→ 接现有整平 + 挖机。
2. **骨架 / 塔架搭建**:持续输入**大量建材**(钢 / 结构件),由建造 agent/无人机就地施工,进度随投入累加。
3. **核心 + 配置件**:混合两种来源——
   - **现场造**:在组装场就地的制造模块 + 物料输入,现场加工出某些部件;
   - **预制运入**:别处流水线做好大件,用 **L3 特殊运输** 运到组装场。
   各配置件是子任务,全齐才算该阶段完成。
4. **调试 / 通电 / 装燃料** → 满足即可点火。

- **多台**:同一 build-plan 的多个实例;需布置在行星**同一侧/朝向**,推力才同向合成(见 §4.2 推力方向)。
- **扩展**:不同 tier/型号发动机 = 不同 build-plan 数据(阶段数、材料量、现场产能要求不同),引擎不变。
- 组件/系统:`ConstructionProject`(当前阶段、各阶段需求与进度、部件清单)+ `ConstructionSystem`(推进阶段、消耗输入、派发建造 agent、广播阶段/整机完成)。
- 建造 agent(builder kind)复用 agent 框架:把材料从物流端口搬到工地并"施工"(类似挖机在作业点作业)。

### 10.6 组件 / 系统 增补(并入 §3)

| 新增组件 | 关键字段 |
|---|---|
| `OreColumn` / `oreColumn(dir)` | 各深度层的 `{item, 深度区间, 储量, 硬度}` |
| `Belt` | 段几何(测地线)、物品队列、进/出端口 |
| `TransportStation` / `TransportRoute` | source/sink、货单、站点序列、绑定运输器 |
| `PowerTower` | `range, gridId, 容量` |
| `Power` | `demand, supply, gridId` |
| `Colonist` / `Population` | 数量、需求、满意度、增长 |
| `DevelopmentLevel` | 多维发展度(派生) |
| `ConstructionProject` | 阶段索引、各阶段需求/进度、部件清单 |

| 新增/扩充系统 | 职责 |
|---|---|
| `MiningSystem` | 挖机作业 → 按挖穿的层产出物质(接 `applyEdit` + `oreColumn`) |
| `LogisticsSystem` | 统一 port 供需调度;Belt/Agent/Route 三策略 |
| `PowerSystem` | 覆盖/电网连通(并查集)+ 满足率结算 |
| `PopulationSystem` | 人口/需求/满意度/增长 → 派生发展度 |
| `ResearchSystem` | 按发展度阈值 + 附加条件解锁(事件广播) |
| `ConstructionSystem` | 发动机分阶段建造推进 |
| `EngineSystem` | 点火后消耗物质 → 推力(接 nbody) |

### 10.7 对路线图(§5)的影响(修订)

- **M1 采矿**:加入"分层矿柱 + 表土剥离"(先挖表土才出矿)+ 机种数据驱动。
- **M2 物流**:拆成 **M2a agent 短途** 与 **M2b 传送带(厂内)**;**L3 定制路线** 放到中后期(M5~M6 附近,发动机需要长途运大件时)。
- **M4 电力**:改为"输电塔覆盖 + 自动连线 + 并查集电网"。
- **M5 科技**:改为 **M5 人口/小人系统 + 发展度**,科技解锁挂在发展度上;科研建筑变成"发展度加成"。
- **M6 发动机建造**:改为 **ConstructionProject 分阶段**(选址平整 → 骨架 → 核心/配置件[现场造+预制运入] → 调试),多台合推。
- 其余(M0 骨架、M3 生产、M7 点火推力、M8 逃逸、M9 打磨)不变。

### 10.8 本轮新增的设计要点小结

- 采矿=**深度分层**,把"挖地形"与"取矿"统一(也和"发动机烧星球物质"共账)。
- 物流=**三层策略**,统一到 port 抽象,方式可插拔。
- 电力=**覆盖即连线**,并查集组网,零手动布线。
- 科技=**经营殖民地(小人发展度)驱动**,生产转为服务民生,间接解锁。
- 发动机=**数据化的分阶段建造工程**,现场造+预制运入混合,多台同向合推。
- 全程坚持:**机种/物品/配方/科技/发动机 build-plan 皆数据** → 加内容不改引擎。
